# 真机接入指南

这份文档回答一个问题：**这套仿真里的算法，拿到真机上还成立吗？哪里必须重做？**

结论先说：**算法层可迁移，标定层必须重做。** 具体是哪些、为什么、怎么验，下面逐条给出，并且所有数字都是在本工程实测得到的。

---

## 1. 最需要先说清的一件事

`tests/test_mujoco_workcell.py` 里有一个看起来很有说服力的测试：

```python
def test_mujoco_fk_matches_official_urdf(self):
    w.set_q(q)
    np.testing.assert_allclose(w.flange_pose(), w.kin.fk(q), atol=1e-9)
```

但 `w` 是 `World`，而 `World` 的 MJCF 是由 `model_builder.build_model_xml()` 从**同一份 URDF** 生成的：

```python
urdf = E.parse(ROOT / cfg['robot']['urdf']).getroot()   # model_builder.py:32
...
pos, R = origin(joint)
E.SubElement(base, 'body', name=name, pos=numbers(pos), quat=quat(R), ...)
```

所以它证明的是：

> **我们的 URDF 解析器** 与 **MuJoCo 对我们生成的 MJCF 的解释** 一致到 1e-9

这是一个很硬的**内部一致性**检查 —— 它能抓住解析 bug（比如 RPY 顺序写反、四元数 xyzw/wxyz 搞混），但**它完全没有接触真机**。两边同源于一个文件，同错则同错。

**读这条测试时不要产生「FK 已验证与真机一致」的误解。**

## 2. URDF 里有什么、没有什么

六个关节的完整定义：

```
joint1_to_base     xyz=0 0 0.205        rpy=0 0 0             axis=0 0 1    limit=[-3.14, 3.14159]
joint2_to_joint1   xyz=0 0 0            rpy=1.5707 -1.5708 0  axis=0 0 -1   limit=[-3.14159, 3.14159]
joint3_to_joint2   xyz=0.269 0 0        rpy=0 0 0             axis=0 0 -1   limit=[-2.61, 2.618]
joint4_to_joint3   xyz=0.266 0 -0.088   rpy=0 0 1.5708        axis=0 0 -1   limit=[-2.9670, 2.9670]
joint5_to_joint4   xyz=0 -0.095 0       rpy=1.5707 -1.5707 0  axis=0 0 1    limit=[-2.93, 2.9321]
joint6_to_joint5   xyz=-0.053 0 0       rpy=-3.14159 0 3.14159 axis=-1 0 0 limit=[-3.03, 3.0368]
```

只有三样东西：

| 有 | 说明 |
|---|---|
| `origin` (xyz + rpy) | 相邻关节的几何关系 |
| `axis` | 转轴方向（在各自动关节坐标系内） |
| `limit` | 关节限位 |

**没有**（这些在真机 SDK 里一定存在）：

| 没有 | 后果 |
|---|---|
| 编码器零位偏置 `joint_zero_offset` | 同样的 `q` 值，真机位姿与仿真不同 |
| 减速比 `gear_ratio` | SDK 的 `get_angles()` 读数经过换算，URDF 不知道 |
| 连杆长度标定值 | 加工/装配误差累积 |
| TCP 偏移 | SDK 的「末端」常带工具补偿，URDF 的 `link6` 是纯几何原点 |

**一个观察**：关节 1、2 的限位恰好是 ±π：

```
joint1: [-179.91°, 180.00°]
joint2: [-180.00°, 180.00°]
joint3: [-149.54°, 150.00°]     ← 不对称，像真实值
joint4: [-170.00°, 170.00°]
joint5: [-167.88°, 168.00°]
joint6: [-173.61°, 174.00°]
```

关节 3–6 是不对称的「真实值」，而 1、2 正好卡在 ±180°。后者通常意味着**按 ±π 占位**，不是数据手册值。接入前必须核对。

## 3. 差异有多大：实测敏感度

用 `outputs/demo` 的 12 个真实视点做敏感度分析。

### 3.1 单关节零位误差

给某一个关节单独加一个零位偏差，看相机光心位移（对 12 个视点取统计）：

| 误差角 | 最大位移 | 平均位移 | 对比 3 mm 预算 |
|---:|---:|---:|---|
| 0.1° | 0.83 mm | 0.39 mm | 预算内 |
| **0.5°** | **4.15 mm** | 1.96 mm | **已超出** |
| 1.0° | 8.31 mm | 3.92 mm | 超出 2.8 倍 |
| 2.0° | 16.62 mm | 7.84 mm | 超出 5.5 倍 |

### 3.2 整臂零位偏置（6 个关节同时偏）

| 偏置 | 最大位移 | 最小位移 |
|---:|---:|---:|
| 0.1° | 1.64 mm | 1.22 mm |
| 0.2° | 3.29 mm | 2.44 mm |
| 0.5° | 8.23 mm | 6.10 mm |
| 1.0° | 16.49 mm | 12.16 mm |

**为什么 3 mm 是关键数字**：`feasibility.padded_food_corners()` 给 Food ROI 各边外扩 `roi.margin_m = 3 mm`，这是留给标定误差的边界预算。**整臂偏 0.2° 就已经吃掉整个预算**，偏 0.5° 则让「刚好通过边距检查」的视点在真机上被裁掉。

这个 3 mm 不是随便定的，它就是为这类误差准备的。反过来说：**如果实测零位误差超过 0.2°，应该先调大 `roi.margin_m`，再重跑**。

### 3.2b 两个不同的「mm」，不要混为一谈

上面 3 mm 是**图像边距**（`roi.margin_m`），决定食材会不会被裁出画面。真正管机械臂
不撞东西的是另一个数：`motion.collision_margin_m`，当前 **10 mm**。它是
`Checker.violation()` 的判据，因此是**唯一被代码强制**的安全间隙。

实测这两个预算的余量完全不同：

| 预算 | 数值 | 0.2° 整臂偏置（3.29 mm）的效果 |
|---|---|---|
| `roi.margin_m` 图像边距 | 3 mm | **吃掉 110%**，刚好通过的视点会失效 |
| `collision_margin_m` 碰撞裕度 | 10 mm | 吃掉 33%，仍剩 6.7 mm |

而实测的臂到场景最小间隙是 **41.08 mm**（见 `docs/validation.md`），按 0.2° ≈ 3.3 mm
换算允许约 **2.7°** 的整臂等效角度误差。

**所以真机部署时的校验顺序是：先标定（第 6 节），再读实测零位误差，然后决定是否需要
调大 `roi.margin_m`。** `collision_margin_m` 反而不必因为标定而改动 —— 它的 10 mm
上限由 `col_link5` ↔ `col_camera_bracket` 这个被螺栓固定的结构常数决定，不是由运动
决定的。

### 3.3 单位错误

Elephant Robotics 的 Python SDK 大量使用**角度**，而本工程全程**弧度**。忘记换算的后果：

```
正确 q (rad): [-2.598, -0.439, -0.757, -0.752, 1.347, -0.546]
误用 q (deg): [-148.829, -25.138, -43.387, -43.059, 77.201, -31.277]
→ 光心偏移 704 mm（0.70 m）
```

这不是「偏差」，是**完全错乱**。不会产生「略微不准」的结果，会直接被限位拒绝或撞到工位。

### 3.4 单关节符号错误（`q[j]` 该是负的却给正的）

| 关节 | 平均位移 | 最大位移 |
|---|---:|---:|
| joint1 | 308 mm | 463 mm |
| joint2 | 205 mm | 572 mm |
| joint3 | 554 mm | 707 mm |
| joint4 | 164 mm | 245 mm |
| joint5 | 249 mm | 256 mm |
| **joint6** | **0 mm** | **0 mm** |

### 3.5 joint6 的特殊性：位置检查抓不到它

上表最后一行的 **0 mm** 不是笔误。原因是几何巧合：

```
相机相对法兰的安装偏移 T_FC[:3,3] = [0.075, 0, 0]   ← 沿法兰 X 轴
URDF joint6 的转轴 axis = [-1, 0, 0]                ← 也沿法兰 X 轴
```

**偏移向量与转轴共线**，所以绕 joint6 自转**不改变光心位置**，只改变朝向。实测：

```
h00_c0001: 位置差 0.00 mm   朝向差 62.55°
h00_c0002: 位置差 0.00 mm   朝向差 68.26°
h00_c0003: 位置差 0.00 mm   朝向差 33.22°
```

**接入时的直接后果：只验位置无法发现 joint6 符号错误。必须同时验朝向。**

而 62° 的朝向错误意味着图像完全拍偏 —— 但你的位姿检查会全部通过。这是这份清单里最隐蔽的一个坑。

## 4. 风险清单（按严重性排序）

| # | 差异源 | 可能性 | 后果 | 检测手段 |
|---:|---|---|---|---|
| 1 | **单位**（角度 vs 弧度） | 高 | 完全错乱（0.7 m 级） | 读回的 `q` 范围是否超出 ±π |
| 2 | **关节零位偏置** | 几乎一定 | 整体平移 1–8 mm | 多点位姿比对 |
| 3 | **joint6 符号** | 可能 | 位置 0 变化、朝向偏 60°+ | **必须单独验朝向** |
| 4 | 其他关节符号 | 可能 | 0.16–0.7 m | 位姿比对（明显） |
| 5 | 法兰 ≠ TCP | 很可能 | 系统性偏移 | 确认 SDK 的末端定义 |
| 6 | 限位值（1、2 是 ±π 占位） | 可能 | 仿真可达、真机拒绝 | 逐关节比对限位 |
| 7 | 到位精度（伺服滞后/背隙） | 一定 | 毫米级，非零位误差 | 读回实际角 vs 目标角 |

## 5. 哪些可以放心迁移

不要以为「全都要重做」。以下内容**与具体硬件无关**：

| 内容 | 为什么可靠 |
|---|---|
| **FK / IK 的数学本身** | 给定相同的关节角与相同的连杆几何，任何正确的 FK 结果相同。差异只来自输入（零位）与几何（标定） |
| **几何门禁（`feasibility`）** | 全在图像与几何空间，不关心机器人怎么到达 |
| **图像验收（`quality`）** | 同上 |
| **光轴去重（`diversity`）** | 只比较朝向向量 |
| **RRT-Connect 与碰撞检查** | 只要传入的 `q` 是「真机意义上的关节角」，算法成立 |
| **数据格式与统计契约** | 与硬件完全无关 |
| **`T_BC = T_BF · T_FC` 变换链** | 刚体变换代数，不因机型而变 |
| **确定性设计（四条随机流）** | 与硬件无关 |

**唯一需要在标定层重做的是：关节角 ↔ 位姿的映射。**

## 6. 接入流程：先测量，再吸收

**核心原则：不要「调代码让它对上」，要先测出差异，再决定在哪一层吸收。**

### 第 1 步：只验 FK，不动机械臂

选 5–10 个姿态（覆盖工作空间，不要都挤在 home 附近）。每个姿态：

1. 从 SDK 读 6 个关节角 → 先确认单位，**转成弧度**
2. 用 `kin.fk(q_sdk) @ T_FC` 算出预期相机位姿
3. 用外部手段测实际法兰位姿（贴标记 + 相机，或触点测量）

记录**位置偏差**和**朝向偏差**（两个都要，见 §3.5）。

### 第 2 步：判断误差类型

| 现象 | 判断 | 处理 |
|---|---|---|
| 各姿态偏差**方向一致、大小接近** | 零位问题 | 用 `joint_zero_offset_rad` 吸收 |
| 偏差**随姿态变化** | 几何误差（连杆长度/轴方向） | URDF 需修正，不能靠偏置修 |
| **位置对、朝向错** | joint6 符号或 TCP 朝向 | 单独查 joint6 |
| 偏差 > 100 mm | 单位或符号错误 | 回到第 1 步检查输入 |

### 第 3 步：把标定结果放进配置，不要改代码

推荐新增（当前 `configs` 里**没有**这个字段）：

```json
"robot": {
  "joint_zero_offset_rad": [0, 0, 0, 0, 0, 0],
  "joint_sign": [1, 1, 1, 1, 1, 1]
}
```

然后在关节角进入 FK **之前**应用：

```python
q_calibrated = q_sdk * np.array(cfg["robot"]["joint_sign"]) - cfg["robot"]["joint_zero_offset_rad"]
```

这样做的三个好处：

1. **仿真基线不受影响**（默认全 0 / 全 1）；
2. 换一台机器只改配置；
3. 差异来源可追溯，不会变成散落在代码里的魔法修正。

### 第 4 步：核对限位

逐关节比对 SDK 的实际限位与 URDF 的 `limit`。**关节 1、2 的 ±π 尤其要确认** —— 如果真机是 ±170°，仿真在 175° 附近的采样在真机上直接不可达。

### 第 5 步：放宽到位容差，改用「读回实际值」

本工程在仿真里测到的到位误差：

```
camera_position_error_m      最大 0.141 mm
camera_rotation_error_deg    最大 0.023°
```

这是**理想位置伺服**的结果。真机会大 1–2 个数量级（毫米级）。所以：

```json
"robot": {
  "ik_position_tolerance_m": 0.0005,      // ← 0.5 mm，真机上大概率超差
  "ik_rotation_tolerance_deg": 0.1
}
```

接入真机时这两个值必须放宽（比如 2–3 mm / 0.5°）。

**好消息是架构已经支持这件事**：`planner` 在到位后会重算实际位姿并重新跑几何与质量检查（`planner.py` 第 106 行），不合格的候选会被记为 `arrived_*` 拒绝。所以真机的毫米级误差会被当作**正常误差处理**，而不是让流程失效 —— 只要容差设得合理。

## 7. 一张对照表：仿真 vs 真机

| 维度 | 仿真 | 真机 | 是否需重做 |
|---|---|---|---|
| 关节角 → 位姿 | URDF 几何 | URDF 几何 + 零位/减速比/标定 | **是** |
| 碰撞检查 | 凸包 + `mj_geomDistance` | 需换真实模型或保守包围 | **是** |
| 路径执行 | 位置伺服，理想 | 有滞后、背隙、下垂 | **是** |
| 到位精度 | 0.14 mm | 1–3 mm | 放宽容差 |
| 图像 | 几何真值渲染 | D405 双目重建 + 噪声 | **是** |
| 深度 | z-buffer | 结构光 + 反光失效 | **是** |
| 几何门禁 | 纯数学 | 同 | **否** |
| 图像验收算法 | 纯数学 | 同（阈值需重标） | 算法否、阈值是 |
| 光轴去重 | 纯数学 | 同 | **否** |
| 路径规划算法 | 自研 RRT-Connect | 同 | **否** |
| 数据格式/统计 | 纯 Python | 同 | **否** |

## 8. 最小可行验证脚本（接入当天跑）

下面这段只用本工程的代码 + SDK 读数，就能判断「能不能直接用」。**已用仿真数据自检过**：把仿真位姿当作「真机实测」输入，偏差应为 ~1e-10；注入 0.5° 零位误差后应读出约 8.25 mm。

```python
import numpy as np
from scipy.spatial.transform import Rotation
from viewpoint_sim.config import load_config, ROOT, mount_transform
from viewpoint_sim.kinematics import Kinematics

cfg = load_config('configs/default.json')
r = cfg['robot']
kin = Kinematics(ROOT/r['urdf'], r['flange_link'], r['base_position_B_m'])
T_FC = mount_transform(cfg)      # camera.mount 是 dict，必须经这个函数转成 4x4
                                 # 本函数验法兰位姿，暂不需要 T_FC；
                                 # 若要比相机位姿，把 T_pred 换成 kin.fk(q) @ T_FC

def measure_once(q_sdk_deg, T_measured):
    """q_sdk_deg: SDK 读的 6 个角（度）  T_measured: 外部测得的实际法兰位姿 4x4"""
    q = np.radians(np.asarray(q_sdk_deg, float))       # ← 单位换算
    T_pred = kin.fk(q)                                  # 法兰位姿 T_BF
    dpos = np.linalg.norm(T_pred[:3,3] - T_measured[:3,3]) * 1000        # mm
    drot = np.degrees(Rotation.from_matrix(
        T_pred[:3,:3].T @ T_measured[:3,:3]).magnitude())               # deg
    return dpos, drot

# 收集 5-10 个姿态后按下表判断：
#   位置 < 0.5 mm                -> URDF 几何可用
#   位置 1-8 mm 且方向一致        -> 零位问题，标定 joint_zero_offset_rad
#   位置对但朝向偏 30-70°         -> 查 joint6 符号（见 §3.5）
#   位置偏 > 100 mm              -> 单位或符号错误，回到第 1 步
```

## 10. 一句话总结

**会不一样。** 最主要的差异是**关节零位**（整臂偏 0.2° 就吃掉全部 3 mm 标定预算），其次是单位、符号、TCP 定义和限位。

现有 FK 测试只证明了「解析器与 MJCF 生成器对同一份 URDF 的理解一致」，**不是**与真机的一致性验证。

算法的数学部分可以放心迁移，但**必须在实机上做一次 FK 标定**，把结果作为配置项（`joint_zero_offset_rad` / `joint_sign`）放进 `configs`，而不是改代码去凑。

**特别注意 joint6**：它的符号错误不会改变光心位置（因为相机安装偏移与转轴共线），只改变朝向 60° 以上。**只验位置的接入检查会漏掉它。**
